# SQLDelight for storage, checked against Android 10's SQLite

duit-log keeps its data in SQLite through SQLDelight 2: the schema and queries are `.sq` files in `core`, the JVM tests run them on `sqlite-driver` (an in-memory sqlite-jdbc database) and the app runs the same generated code on Android's own SQLite through `android-driver`. SQLDelight's runtime is plain Kotlin, so `core` stays free of Android and keeps passing `checkNoAndroidDependencies`. The phone's SQLite is older than the tests' (3.22.0 on Android 10, the minimum, against 3.53 in sqlite-jdbc), so the schema is compiled with the `sqlite-3-18` dialect: SQL that Android 10 can't run (window functions, `RETURNING`, upsert) fails the build instead of the phone. Checked in ticket 01: `StorageCheckTest` runs the schema on the JVM, the app runs the same check in an in-memory database on start (log line "storage check passed on SQLite <version>"), and on an Android 10 (API 29) emulator it reported SQLite 3.22.0; a window function in a `.sq` file was rejected at build time.

**Considered Options:** Room 2.8 with the bundled SQLite driver (`androidx.sqlite:sqlite-bundled`) runs the same SQLite build in tests and on the phone, which removes the version gap. But its entities and DAOs would sit in `core` as `androidx.room` code with KSP and the Room Gradle plugin, which breaks the "core has no Android libraries" rule the build enforces, and the bundled native SQLite adds a few MB per ABI to the APK.

**Trade-offs:** tests run on a newer SQLite than the phone, so behaviour that differs between versions without a syntax change (query planner, edge cases in built-in functions) is only caught on a device. Migrations are hand-written `.sqm` files.
