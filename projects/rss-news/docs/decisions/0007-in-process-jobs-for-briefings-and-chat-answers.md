# Run Briefings and Chat answers as in-process jobs, not on a job queue

Writing a Briefing or a Chat answer used to happen inside the HTTP response, so leaving the page stopped it and nothing was saved. Each one now runs as a job in a thread of the server process (`jobs/running.py`), which saves its result and keeps its events in memory so a page can follow it, leave, and follow it again (`GET /api/jobs/{id}`). There is one user and at most a few jobs at a time, so a separate queue and worker (Redis, a jobs table polled by a worker, Celery) would add a service to run and monitor for no real gain.

**Trade-offs:** a server restart or deploy mid-job loses the job: what it had written is not saved, and no Alert is sent. It must not look like it hangs, so job ids are random (one from before a restart never names a new job), the server answers 404 for a job it doesn't know, and the PWA shows that as the Briefing or question having failed. A dropped stream ends with an error too, never an endless spinner. Finished jobs are kept for following again only until 50 newer ones have finished. If restarts mid-job become common, persist a job row per job and mark the running ones failed at start-up.

**Later: Simple summaries.** Summarise on an Item runs as a job the same way (one per Item; pressing again while it runs follows it), so leaving the Item no longer loses the summary, and the finished summary is saved for its Item. It sends no Alert: a summary takes seconds, so the owner is usually still there. The Item check and the spending limit still answer 404 and 429 before the job starts; an Item with no text is only found once its page is fetched, so that refusal comes as the job's `failed` event.
